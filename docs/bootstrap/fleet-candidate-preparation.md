# Single-target fleet candidate preparation

Governing issue: [#62](https://github.com/OMT-Global/bootstrap/issues/62).

`src/upgrade-preparation.ts` is an internal source-preparation component. It is
absent from the package index and CLI. It composes the owned public-policy
observation, generator capture and raw-Git snapshot helpers; inventory JSON is
neither an accepted input nor authority to change a repository.

## Inputs and preparation

`prepareObservedUpgrade` accepts a genuine `PolicyObservation`,
`PublicGeneratorCapture`, `VerifiedGitSnapshot`, the absolute original checkout
path, and optional cancellation signal. Copied or reconstructed descriptions do
not recreate the helpers' process-owned associations. The generator capture must
match the observation; the complete raw snapshot must match its public base
commit and tree. The requested policy version must advance.

`preparePublicUpgrade` in `src/upgrade-history.ts` obtains the input snapshot
through the fixed anonymous Git transport. It fetches the observed commit into
a fresh private Git directory and reuses the pack audit used for later candidate
history acquisition. It verifies the raw commit, exact tree and bounded stream
of regular blobs, rechecks the public repository's numeric identity and default
branch head, then removes the temporary Git directory before preparation begins.

Before and after staging, anonymous bounded reads recheck the public repository's
numeric identity, visibility and default head, the Flow publisher identity, and
both policy selectors. The original ordinary checkout is audited against the
same raw snapshot and exact public origin before and after staging. The private
checkout audit fingerprint is compared internally and never returned.

Preparation uses a fresh neutral data repository. The actual current manifest,
resolved policy, renderer output, ownership sidecar and executable modes must
already match the captured public source. An unchanged real `applyRepo` creates
local state in the staging repository's `.git`; an unchanged second plan and
exact file comparison confirm that this did not rewrite the public source.
Committed fallback/home state is unsupported.

Only then is the target policy applied. Its exact observed raw bytes replace the
existing unmanaged policy input. That input cannot overlap managed paths, legal
inputs or state/control files. A Bootstrap-managed manifest is regenerated by
the renderer. For a project-owned manifest, only the two existing policy pin
tokens change; unrelated UTF-8 bytes, comments and line endings are preserved.
Ambiguous YAML selectors fail without a normalized-rewrite fallback.

The target uses the actual planner, apply operation, manifest/policy reload and
second unchanged plan. A complete byte/mode walk must match the intended target
projection plus unrelated original files. Raw Git blob/index operations compute
the candidate tree without target hooks, attribute conversion, `git add` or a
fabricated commit. Successful cleanup is required before a handle is returned.

## Output and next consumer

`describePreparedUpgrade` returns immutable public identities, policy transition,
candidate tree/source digest and changed paths. `copyPreparedUpgradeSource`
returns independent file-byte copies and the genuine original base snapshot.
`discardPreparedUpgrade` releases the process-owned association; cancellation
also disables subsequent access. Copies cannot mutate the stored candidate.

Every output explicitly reports `authority: none`, `pilot: unverified`, and
pending hook, signing, final-check, independent-review and publication gates.
The output is a historical source candidate, not a lease on a public branch or a
proof that a later validation profile will support it.

The next integration must acquire and verify the real base history required by
the isolated backend, establish the actual branch/message/author/committer plan,
and run the existing prepared-hook → trusted signing → final candidate check →
independent review → create-only publication sequence. It must bind each result
to these exact source bytes and recheck live policy/repository/pilot governance
before a write. No signing identity, base-history bundle, isolated execution
receipt, approval or GitHub App capability is manufactured here.

The owner-selected one-repository GitHub App publisher and manual reconciliation
after uncertain writes remain a separate implementation. This component neither
obtains credentials nor executes hooks, signs commits, creates a branch/PR,
updates inventory/pilots, or rolls out a fleet. It does not complete issue #62.

## Validation boundary

The implementation retains ADR-0016's original-checkout/data-helper separation
and existing file, path, byte and Git-command bounds. Preparation has a 15-minute
cancellation deadline. These are per-operation limits, not a new cumulative
allocation accounting contract or immunity to concurrent filesystem replacement.

Tests use real temporary Git repositories, raw objects, checkout audits, owned
observations and current/target rendering. HTTP responses and host eligibility
are fabricated; Linux/prlimit and trusted ancestor ownership are simulated only
for the disposable test fixtures. They do not establish Linux sandbox runtime,
Docker integration, model review, App authorization or real fleet-pilot success.
