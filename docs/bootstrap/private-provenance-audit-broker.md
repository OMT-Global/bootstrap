# Broker delivery of private audit events

`createPrivateRoleReadBrokerAudit` supplies the existing read coordinator's audit port. The worker obtains the audit origin, peer SPKI, expected audit signer and current policy from its verified deployment. It validates the submission's event, signed scope and state version before opening the protocol connection. The caller cannot choose a target, token, signing key, socket or proof payload.

The broker uses a dedicated, non-resuming HTTPS agent. Node validates the server certificate and hostname, and the broker checks the enrolled SPKI before writing either request. It accepts a framed challenge only from the configured endpoint. The second request must use the very same live socket. The broker checks the challenge, token, current configuration and key deadlines when Node assigns that socket. If the socket changes or any deadline passes, it sets neither credential header and sends no submission bytes. The transport follows no redirects and retries neither request.

The broker requests a fresh GitHub Actions token for the endpoint origin followed by `/audit`. It verifies the token against its enrolled workflow and active native run. A short-lived exact custody lease reads only the broker's configured transport key object at `keys/transport/v1/<configEpoch>/<fingerprint>.pkcs8.kms` and unwraps it with the exact workload-transport purpose, owner, key fingerprint and epoch. Semantic signers keep their own custody paths. The broker signs only the canonical workload proof covering its challenge, origin, audience and exact submission digest, never arbitrary request data. The token and proof go only to the configured audit endpoint.

Before returning a response to the coordinator, the broker rechecks current configuration and verifies the canonical acknowledgment against the enrolled audit key, exact event and operation, phase, epoch, version, object key and 90-day retention. The server and broker retain separate proof and audit signing keys. Ambiguous delivery fails closed without retry or another plaintext release.

Provisioning the signed transport custody descriptor, private listener TLS configuration, protected HTTPS and GitHub runtime access, and restricted live provider qualification remain deployment responsibilities. Local wire tests bridge fabricated TLS sockets into the actual listener without opening a network connection.
