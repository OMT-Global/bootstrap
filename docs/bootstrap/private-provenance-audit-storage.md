# Private read audit ingress and storage

The read coordinator carries the version ID returned by each successful S3 state transition into the corresponding audit submission. Revocation and failure records use the verified state version they observed. The existing canonical audit event remains unchanged. The separate private submission carries signed request and approval evidence and the exact canonical state bytes, key and version so the audit worker can authenticate the scope and retain the transition binding. It never carries the decrypted evidence.

The audit ingress requires an enrolled audit worker and a negotiated live TLS connection with the deployment-pinned local SPKI. It issues a one-use random challenge for that socket. The caller must present a signed GitHub Actions OIDC token with the exact enrolled read-broker workload claims and audit-only audience, the configured audit origin followed by `/audit`. The separately enrolled transport key signs the challenge, endpoint and complete submission digest. The worker verifies native GitHub run, attempt, job and reusable workflow state, then rechecks current deployment configuration. The input cannot supply a root of trust, signer, provider, clock or destination.

The audit worker checks the signed request/delegation/approval or revocation and its event subject, actor, purpose, state key, revision and phase. The requester must be enrolled for the subject repository, purpose and approved categories. The installed policy can shorten the signed delegation's approval duration. A read attempt binds the reserved state version, and completion binds the spent version. The session proof attributes the state claim to the trusted enrolled broker. The worker checks that proof and body digest before querying GitHub or S3. Its existing GitHub observation token must be able to read both enrolled runtime job contexts, such as when the broker and auditor run in the same repository. It has no state-bucket read permission.

Only this ingress can admit a record to storage. With the broker run and configuration rechecked, the audit worker writes the event once, with SHA-256, service-key SSE-KMS and a 90-day Governance retention date in the dedicated audit bucket. It reads back the same version and checks body, checksum, encryption, transition metadata and retention. Exact-object STS policies scope the writer and verifier to that operation and the common config pointer. The worker keeps transition metadata private. Unknown write outcomes, duplicate event IDs, missing verification, expiration and connection teardown fail closed. There is no retry or automatic duplicate acknowledgment.

This slice supplies the ingress and verified storage evidence. A fixed bounded HTTP transport must supply the live TLS socket, signed proof, dedicated audience token and canonical submission while enforcing input limits before buffering. The broker's proof transport, audit key custody, signed acknowledgment and fixed runtime composition remain separate. Source tests use fabricated GitHub and AWS responses. Provider policy, TLS termination, retention durability, operational audit health and deployment are separate qualification work.
