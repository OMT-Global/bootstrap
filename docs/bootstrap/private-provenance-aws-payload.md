# Inactive AWS payload operations

This source-only #161/#63 component implements the accepted ADR-0060 payload storage boundary. It has no CLI or workflow caller and performs no operation when imported. Deployment, enrollment, credentials, real capture and provider qualification remain separately authorized work. It composes the committed opaque identity foundation with the shared codec; synthetic APIs remain unchanged.

`putPrivateRoleCiphertext(identity, bytes, intent, signal?)` accepts only a genuine live `capture` identity. `inspectPrivateRoleCiphertext(identity, locator, capturedAt, signal?)` accepts only a genuine live `ciphertext-verifier` identity. Structural objects, other roles and disposed/expired handles fail before cloud work. Signed deployment fixes region, account, payload bucket and distinct client/service KMS keys; the fixed payload prefix is `payloads/captures/`. Intent UUID, timestamps and locator are bounded data, not proof of producer admission or capture authorization. The future capture coordinator must bind them to its verified admission and public envelope; these primitives never issue a capture receipt.

The original identity session remains configuration-read-only. Each operation freshly verifies the native run/attempt/job and root-signed current configuration, then exchanges the already verified token for a separate exact-object STS session. Both temporary and initial clients have explicit credentials, fixed us-east-2 endpoints, no region redirect, default credential lookup or SDK retry. No client, credential, arbitrary command or caller-supplied transport callback is exported. The temporary session is destroyed after the operation; disposal and cancellation abort in-flight work.

Write session policy confines upload and retention permissions to that single UUID key, and service-key GenerateDataKey to regional S3 with that object's encryption context. The PutObject statement requires the conditional header, Governance mode, exact retention instant and SSE-KMS key. The separately evaluated PutObjectRetention permission is confined to the same object, mode and exact instant; it uses only condition keys supported for that action. No post-create retention API is exposed. IAM alone cannot distinguish initial assignment from an identical same-object retention request; the exact mode/date grant cannot authorize a different retention value. Its SDK request has `IfNoneMatch: *`, bounded complete bytes, full SHA-256, exact owner/key and disabled Bucket Keys. The supplied trusted capture time must be no later than the worker clock and no more than the configured 60-second skew old when writing; retention must be exactly capture time plus 90 days. Errors including 409, 412, timeout and missing version fail without retry or deletion. A successful return is only an unverified locator, never a receipt or a claim of end-to-end capture.

Verification session policy permits only GetObjectVersion/GetObjectRetention for the exact key, with corresponding S3-only service-key Decrypt. GetObjectVersion additionally has the exact VersionId IAM condition. S3 provides no version-id condition for GetObjectRetention, so its grant is object-specific and the unexported SDK request always supplies the exact VersionId. It has no client-key decrypt or write authority. The adapter rejects partial/multipart/deleted/SSE-C responses before normalizing harmless SDK fields, requires the full-object checksum and exact service/client-key binding, consumes bounded ciphertext, and checks exact version/length/hash. LastModified must be within the enrolled 60-second capture-clock tolerance; capturedAt must be past and the 90-day interval unexpired. Separate exact-version retention read must show Governance and precisely capture time plus 90 days. The capture interval is rechecked before payload/retention requests and after the final freshness read, so expiry during an awaited operation cannot yield successful inspection. Native activity and active configuration are freshly rechecked before returning either upload or inspection results. Long otherwise-valid identifiers that exceed STS's inline policy bound fail closed.

The complete operation has a 30-second deadline and a bounded stream/chunk count. Late bodies received after cancellation are destroyed; no retention call follows an aborted read. Raw SDK failures are replaced with a fixed non-sensitive error. No cleanup deletes a retained or uncertain object. A failed post-write refresh leaves an uncertain upload for independently authorized reconciliation.

Fabricated integration tests use actual signed fixture JWTs and deployment documents with mocked SDK/fetch boundaries. They do not qualify IAM conditions, native provider durability, cancellation, Object Lock or real clock health. The fixed worker must be deployed only with independently qualified identity/resource/KMS policies, synchronized clocks and the approved health monitors. State CAS, durable audit, custody/KMS client operations, receipt signing and complete capture/read/gate composition are later source slices.

Provider contracts: [S3 PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html), [action-specific IAM condition support](https://docs.aws.amazon.com/service-authorization/latest/reference/list_s3.html), [exact-version GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html), and [GetObjectRetention](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObjectRetention.html). Provider policy/runtime behavior still requires live qualification before activation.
