# Installed private provenance deployment verification

This source component continues ADR-0060 and #161/#63. It verifies the owner-approved revision-2 DeploymentBinding and ActiveConfig contracts. It is inactive: no workflow, CLI, provider request, credential enrollment, cloud configuration or real evidence capture is introduced. Existing read/storage/control and envelope codecs remain unchanged.

## Inputs and evidence

`verifyInstalledDeployment(bytes, bootstrap, now)` accepts the exact canonical signed binding bytes and protected installation inputs. The owner-authorized installation process must pin external deployment-root public keys and owner IDs, minimum epoch, account/region, configuration bucket and literal `config/active.json`, selected workload ID and purpose, exact role ARN and OIDC subject, and the four administrative identities. Stable IDs represent owner-selected administration; a display login does not authenticate it. The signed document cannot select its own bootstrap authority.

The verifier uses the existing sorted-json-v1 canonicalization, key fingerprint and Node Ed25519 full-payload signature primitives. The binding alone has the reviewed 65,536-byte/depth-8 configuration bound. ActiveConfig retains the 16,384-byte/depth-6 online control bound through `verifyPrivateControl`. Neither changes existing private/public envelope wire formats or bounds. The binding digest is SHA-256 over the complete canonical **signed binding**, including its signature.

All configuration shapes are closed. The verifier requires the complete ten-role registry, unique purpose/role associations, exact account/region/type KMS and IAM ARNs, distinct resource buckets and encryption key purposes, explicit workflow SHA/ref/environment/event/runner associations, three pinned HTTPS endpoint purposes, selected retention/time policy values and the fixed required-check name. It rejects aliases, placeholders, wildcards, reused mathematical signing keys and cross-purpose authority. Configuration validation does not prove that named AWS resources exist or that their provider policies enforce the registry.

Current semantic and transport keys resolve to exactly one enrolled owner. Public exporter/publisher get no provenance semantic or transport authority; capture/read broker get no semantic decision key. An audit transport key is optional when there is no peer endpoint call. Historical/rotation semantic keys may remain in the binding but are omitted from the returned current-owner registry; they grant no current authority. Every transport key must have a current enrolled owner. Existing four-purpose control verification must receive only the applicable subset, never the entire twelve-purpose registry.

`verifyCurrentPointer({bytes,bucket,key}, installed, now)` requires a module-owned installation handle, exact pinned configuration location, current root authority and time bounds, the complete signed-binding digest, config ID and epoch, and minimum-epoch protection. The pointer must use the binding's root signing fingerprint; root-key rotation therefore requires a newly signed installed binding and pointer. Pointer lifetime cannot exceed binding lifetime. The function revalidates installation/key expiry at the time of the pointer check and rejects a clock earlier than the installation verification time. The configured 60-second OIDC tolerance does not extend configuration or key expiration.

Both results are deeply frozen data snapshots backed by module-private ownership records. `inspectInstalledDeployment` and `inspectCurrentDeployment` reject copied, serialized or caller-fabricated lookalikes and recheck current local validity. They are the fixed consumers' access points; TypeScript shape compatibility is not authority. Caller mutation of original byte buffers or bootstrap objects cannot rewrite an existing installation. A new installation handle is required after a trusted pin/configuration change.

## Fixed consumer boundary

The next consumer is `src/private-provenance-identity.ts`: it authenticates GitHub OIDC and native repository/run identity, constructs the exact configuration-only provider capability, performs an authenticated fresh S3 GET, then calls this pointer verifier before constructing any later role capability. That source component is separate work. The protected runtime caller supplies trusted time; these pure verifiers do not acquire a clock or authenticate the caller of their exported functions.

Pointer evidence proves signed content, location agreement and validity **at verification time**. It does not prove a fresh network read, S3 service-key enforcement, ETag/conditional replacement, TLS/JWKS authentication or IAM permissions. Rechecking an old pointer locally cannot substitute for each mandated fresh provider read. The current-pointer-to-action race remains the reviewed bounded in-flight limitation. Rolling back both installed code and its minimum epoch remains an administrative trust limitation.

Each role uses an exact configured customized OIDC subject containing repository, environment and immutable `job_workflow_ref`; both documented name-based and immutable repository-ID syntaxes are parsed, but a configured subject is never normalized or substituted. The selected local subject must equal its out-of-band pin byte for byte. A native identity producer must additionally check numeric repository/owner IDs, reusable and caller workflow identities, event, ref, environment, runner class and approved artifact digest. Merely matching a subject does not authenticate those facts. Configuring the GitHub subject template and IAM trust is a later separately authorized operational step.

The representation follows [GitHub's OIDC subject documentation](https://docs.github.com/en/actions/reference/security/oidc), [IAM resource identifiers](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html) and [KMS key identifiers](https://docs.aws.amazon.com/kms/latest/developerguide/concepts.html). This module selects standard `aws`/`us-east-2` exact resources; no alias, alternate partition or wildcard interpretation is supported.

## Regression scope

Fabricated signed records and ephemeral keys exercise complete enrollment, malformed/oversized/noncanonical input, unknown fields, absent or reused authority, invalid ARN/account/region/workflow/endpoint associations, external bootstrap mismatch, expiry and rollback, root/key canonicalization, historical keys without authority, exact-pointer digest and location, object mutation and forged evidence handles. No real private deployment data, credentials, provider calls or cloud policy simulation is used. These tests qualify source contracts only; operational qualification remains outstanding.
