# Private provenance identity foundation

The inactive `establishPrivateRoleIdentity` entrypoint establishes an owned, config-read-only identity in a trusted GitHub Actions job. It does not activate a workflow, create a role, collect private evidence or grant payload/state/KMS operations. Importing it performs no credential lookup or provider request.

`establishPrivateRoleIdentity` accepts a genuine installed deployment handle from `private-provenance-deployment`. That module verifies the root-signed binding and separately installed account, role, workload purpose, subject, config location and root pins. Structural lookalikes fail. The runtime reads only explicit GitHub Actions token-acquisition variables, `GITHUB_TOKEN`, run ID and attempt; it never discovers AWS credentials from environment, files, profiles or instance metadata. Provider SDK dependencies contain their standard credential-provider packages, but this component supplies its own credentials to both clients and does not invoke that chain.

The Actions request URL is job-specific runtime configuration. Acquisition permits only HTTPS, a single-label `*.actions.githubusercontent.com` provider host, an `idtoken` route and the fixed `sts.amazonaws.com` audience. Credentials never enter a caller-selected URL or exported client. Redirects fail; JSON reads, token sizes and the entire operation have bounds. The installed runtime and its environment remain trusted; these restrictions do not make hostile process configuration safe.

The fixed GitHub issuer/JWKS and maintained `jose` implementation verify an RS256 JWT, exact subject and audience, validity window and all enrolled workflow/repository/environment/event/ref/runner claims. Numeric repository and owner IDs are independent of display names and customized subject formatting. Native authenticated GitHub reads bind the same repository, current run attempt, head repository, actor, commit, active job and check-run identity. A job's `check_run_url` is compared to the signed `check_run_id`; the check ID is not assumed to equal the job ID. Attempt job listings must fit one complete page of at most 100 jobs; larger or incomplete observations are unsupported and deny acquisition.

The deployment contract enrolls an exact subject containing the immutable `job_workflow_ref`; this component therefore supports only the enrolled reusable workflow. It requires signed `job_workflow_ref`/`job_workflow_sha` and a matching native `referenced_workflows` entry. Native caller paths may be bare or qualified by the exact enrolled branch's short/full ref; a supplied suffix is checked before comparing the reconstructed exact signed `workflow_ref`. Wrong, tag-qualified or ambiguous refs fail. Direct workflow jobs lack those reusable claims and are outside this contract. The environment and runner class are GitHub-signed claims compared with deployment enrollment. The native job API is not claimed to expose an environment field. A pinned workflow does not by itself prove which artifact bytes were installed on a runner; the deployment process must enforce its separately registered artifact digest.

Only after those checks does the AWS SDK request `AssumeRoleWithWebIdentity` at the fixed Ohio endpoint. The exact enrolled role, bounded duration and derived run/attempt session name are mandatory. Its inline session policy permits only `s3:GetObject` on `config/active.json` and service-key `kms:Decrypt` through S3 for that same object's encryption context. It grants no list, write, payload, state or custody access. The STS client has no usable bootstrap credential provider. The S3 client receives the returned temporary credentials explicitly. Both use fixed regional endpoints, one attempt, transport timeouts and cancellation; no custom SigV4 or XML parser is implemented.

The returned STS subject, audience, assumed-role ARN and expiration must match. The credentials remain in module-owned state. A fresh authenticated bounded GET of the exact config object checks its service-encryption key and root signature, digest, epoch and validity through `verifyCurrentPointer` before the opaque handle exists. A returned SHA-256 checksum is checked when present; the mandatory root signature authenticates the bytes independently. The mutable pointer need not pretend to be an immutable versioned evidence object. S3 Bucket Keys are unsupported because the fixed KMS policy requires the exact object encryption context.

The handle reveals only workload ID, role purpose and expiry. `refreshPrivateRoleIdentity` repeats native active-run/job checks and obtains another fresh config pointer; cached configuration cannot satisfy it. The handle expires no later than the original JWT, STS credential or deployment expiry. A cancelled caller, disposed handle or changed/expired pointer denies further use. `disposePrivateRoleIdentity` cancels in-flight checks, closes clients and removes local references. It does not revoke an issued AWS session, promise memory erasure or invalidate credentials copied by privileged process inspection. Administrative compromise and provider revocation races remain outside a local observation's guarantee.

The explicit [AWS payload operations](private-provenance-aws-payload.md) now compose this owned handle with separate exact-object sessions; default identity acquisition remains config-only. This foundation exports no raw credentials, SDK client, arbitrary request function, configurable transport or assertion callback. SDK/global-fetch mocking is confined to tests. No CLI or workflow currently invokes the entrypoint.

Runtime dependencies are pinned to `@aws-sdk/client-sts` and `@aws-sdk/client-s3` 3.1169.0 and `jose` 6.2.17. The package's existing Node 20 minimum remains unchanged. Added direct and transitive dependency notices are managed through `project.bootstrap.yaml`; first-party LICENSE bytes are preserved.

Primary API contracts: [GitHub OIDC claims](https://docs.github.com/en/actions/reference/security/oidc), [workflow run attempts](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run-attempt), [workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt), [STS web identity](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html), [AWS SDK client configuration](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/migrate-client-constructors.html), and [jose JWT verification](https://github.com/panva/jose/blob/v6.2.17/docs/jwt/verify/functions/jwtVerify.md).
