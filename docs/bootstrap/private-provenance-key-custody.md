# Private provenance public signer custody

An enrolled `public-signer` workload can construct the existing signed public provenance format for an open PR in an enrolled public repository. It checks the live base repository, base ref and expected head, including the actual fork identity, using its authenticated GitHub workload token. The native review lookup is bounded and verifies stable current reviews before and after signing. An approval must come from a reviewer other than the PR author. A blocking opinion at the expected head stops the operation.

The root-signed active deployment contains a custody descriptor for the enrolled `public-manifest` key. The descriptor pins an exact S3 version ID and the SHA-256 digest of the wrapped bytes. The object is selected as `keys/semantic/v1/<configEpoch>/<fingerprint>.pkcs8.kms` in the deployment's custody bucket. Its contents are the KMS symmetric ciphertext of an Ed25519 PKCS#8 DER private key. The KMS encryption context binds `purpose`, `ownerId`, `fingerprint` and `configEpoch`. Configuration without the custody descriptor cannot sign.

The signing operation acquires a separate short-lived session for that object version, the S3 service KMS key via S3 for that exact object, and the distinct custody KMS key for the exact context. Active configuration reads use the original configuration-only session. The signer verifies the full object checksum, signed ciphertext digest, response key ARN and derived public key fingerprint. Separate checks revalidate the active configuration, enrollment, time and native review context. Temporary AWS clients are destroyed and plaintext bytes cleared. Clearing the SDK buffer cannot guarantee immediate erasure of Node/OpenSSL's internal key object.

The result is canonical signed public envelope bytes no larger than 65,536 bytes. The workload derives the manifest from the verified PR and its native run. Inputs select only the enrolled repository, PR number and expected head. Existing public CLI and synthetic interfaces keep their formats. The workflow and artifact queue remain separate deployment and implementation stages. A signed envelope alone provides neither a private capture receipt nor merge authority. Fabricated-provider tests exercise the source. Real role trust, KMS permissions, object versioning and credential handling need qualification before activation. Cross-repository signing requires a protected short-lived credential with read access to the enrolled workload job and target public PRs. GitHub's built-in Actions token grants repository-scoped permissions. A denied lookup ends the operation without a fallback credential.
