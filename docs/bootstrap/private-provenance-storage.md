# Private ciphertext storage source component

This source-only component follows the independently reviewed private-provenance design revision 2 (manifest SHA-256 `65a28732a4c0fab6f9a9a4fa29a11ca32623ea6944d1392d661b3dd103e8d82d`) and the owner's 2026-11-15 source implementation approval. It does not install an AWS client, obtain credentials, capture evidence, enroll keys or activate a workflow. Existing synthetic APIs and guards remain unchanged.

`createPrivateCiphertextWriter(config, transport).put(bytes, intent)` accepts canonical private-envelope-v1 ciphertext and returns an **unverified exact-version locator**. It constructs one conditional `PutObject` with SHA-256, SSE-KMS, and Governance retention at least 90 days after the trusted capture timestamp. It never retries, reads stored objects, unwraps keys or signs receipts. Unknown or ambiguous upload outcomes fail; a later authorized reconciler must inspect them independently. The intent's UUID is supplied by the trusted capture worker; the storage adapter cannot prove randomness or authenticate its clock.

`createPrivateCiphertextVerifier(config, transport).inspect(storage)` requests the exact version, streams at most 2,097,152 bytes, verifies canonical envelope framing and the actual byte checksum, checks the service-encryption key and version response, then separately requests that version's retention. It returns SHA-256, observed Governance date and service key. It neither decrypts client encryption nor proves that ciphertext's subject, public digest, AEAD tag, capture clock or retention matches a trusted receipt. In particular, `inspect` returns an observed shorter date rather than inventing a compliance pass; the capture/gate consumer must reject any mismatch.

## Named composition and consumers

The planned fixed `ProductionCaptureWorker` is the writer's only ordinary consumer. Before calling `put`, it must verify current signed deployment configuration, capture admission, approved evidence categories, public signature/subject/run, client-key allowlist and fresh data-key/nonce generation. It must not expose this adapter directly to requesters or PR code.

The planned fixed `ProductionCiphertextVerifier` and `ProductionMaterialGate` consume `inspect`. They must compare the returned digest, region/bucket/key/version, service-key ARN and retention date with independently trusted capture intent/receipt and the 90-day policy. The verifier must satisfy all checks before signing a production receipt. The gate must validate that receipt against current exact-head context. These compositions and their AWS authentication adapters remain incomplete and inactive in this slice; callable source interfaces do not establish deployment authority.

Installed config contains only `region`, `bucket`, `prefix` and exact `serviceKeyArn`. The source candidate supports `us-east-2`, a general-purpose bucket, an opaque UUID-v4 capture name under a fixed prefix, and a same-account bucket/service key. `ExpectedBucketOwner` is derived from the KMS ARN account. The fixed deployment loader must verify that this account equals the approved deployment account. Cross-account sinks, aliases, directory buckets, multipart operations, copies, range reads and object-key selection by a requester are unsupported. Object existence, IAM rights and configured identity cannot be inferred from syntactically valid identifiers.

The write transport exposes only `region` and `putObject`; the verification transport exposes only `region`, `getObject` and `getObjectRetention`. Mixed-role port objects are rejected. Narrow interfaces do not themselves enforce IAM: authenticated endpoint selection, OIDC/STS identity, service permissions, read/write separation and the configuration-only active-pointer checks belong to the fixed trusted composition. Neither transport is supplied by a requester. No `verify():true` or success boolean substitutes for returned version/checksum/retention fields.

## Exact operation contracts

The source uses AWS operation parameter names but has no AWS SDK dependency. Each transport returns a strict, normalized projection of an authenticated response. It must bind the response to the exact request and fixed region and must not retry writes. Actual S3 responses do not echo bucket/key; these are constrained in the request and trusted transport, not fabricated response fields.

- `putObject` returns exactly `statusCode:200`, `VersionId`, `ChecksumSHA256`, `ChecksumType:"FULL_OBJECT"`, `ServerSideEncryption:"aws:kms"` and `SSEKMSKeyId`, with optional `BucketKeyEnabled:false`.
- `getObject` returns the same fields plus `ContentLength` and `Body`, an `AsyncIterable<Uint8Array>`. `ChecksumMode:"ENABLED"` is requested. The adapter counts and copies chunks itself and requires exactly the advertised complete size. The transport must reject, or preserve as unexpected fields so this adapter rejects, a response containing `ContentRange`, multipart `PartsCount`, `BucketKeyEnabled:true`, or a delete marker. It must not quietly discard such conflicting metadata while normalizing harmless SDK metadata.
- `getObjectRetention` returns exactly `statusCode:200` and `Retention:{Mode:"GOVERNANCE",RetainUntilDate:<UTC millisecond ISO timestamp>}` for the requested exact version. Other lock/hold modes are outside this candidate. The future transport must normalize authenticated AWS timestamp values without changing their instant; it must not infer or round up retention.

Every operation carries an `AbortSignal` and the adapter has a 30-second whole-operation deadline, including download and retention inspection. The transport and stream must honor cancellation. Timeout rejects and aborts; it does not prove the provider stopped or that an upload never landed. An authenticated adapter must prevent deferred/background calls after abort, expose ambiguous outcomes for reconciliation, and never create a successful receipt from them.

SSE Bucket Keys are disabled on writes to preserve object-level service-key encryption-context scoping. A separate client key must differ from the service key; only the upstream trusted capture/verifier can establish its allowlist. Wrapped-key digest and strict framing checks catch malformed envelopes, but do not authenticate their contents. Malicious data can imitate ciphertext framing; this API is not a plaintext classifier or a substitute for the upstream capture boundary.

## Validation and remaining evidence

Fabricated tests cover exact requests, original size/framing bounds, corrupt streams/checksums, wrong versions/keys, prefix escape, mixed roles, incomplete retention, ambiguous writes, cancellation and sanitized errors. Existing private synthetic and public provenance tests are rerun to protect compatibility. No IAM/OIDC policy, real S3 response, lock state, independent runtime role, provider cancellation behavior or production durability was verified. No source-only result closes #161 or #63.
