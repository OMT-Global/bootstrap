# Public Provenance

`bootstrap provenance create --input provenance-input.json --output provenance/runs/<run>.json` redacts metadata and writes a version-2 public manifest. `bootstrap provenance validate --input provenance/runs/<run>.json` validates it before publication.

The public manifest records the repository, immutable commit SHA, workflow run, reviewer lineage, and explicitly allowlisted metadata. The only metadata keys accepted are `policy`, `generator`, `aiProvider`, `aiModel`, `promptHash`, and `changeClass`; unknown keys and unknown fields at any schema boundary fail validation rather than being copied or silently removed.

Credential-like literals in allowlisted metadata become typed `[REDACTED:CREDENTIAL]` placeholders. Validation rejects credential-like values in identity fields and rejects redaction counts that do not exactly match the emitted placeholders. The detector is defense in depth, not permission to pass arbitrary logs, prompts, tool output, customer data, or other private material into the public generator.

The default validator accepts only version 2 so publication and merge gates cannot downgrade to the permissive legacy metadata shape. Library consumers may use the explicit `readLegacyPublicProvenance` compatibility reader for historical version-1 artifacts; it rejects unknown fields and credential-like literals across recognized public fields. Version 1 still permits arbitrary metadata keys and does not satisfy the current allowlist contract. Migrate by supplying the intended allowlisted fields to `provenance create` and publishing the resulting version-2 manifest rather than relabeling an existing artifact.

Signed envelopes (the issue #61 public slice, ADR-0007): `signPublicProvenance(manifest, { privateKey, signedAt? })` wraps a version-2 public manifest in a strict envelope (`envelopeVersion` 1) carrying an Ed25519 signature over a domain-separated canonical payload — canonical JSON with recursively sorted keys and no insignificant whitespace (`sorted-json-v1`) over `{ algorithm, canonicalization, domain, envelopeVersion, manifest, signedAt }`. Signing uses only `node:crypto` (no new dependencies, no network access), refuses to sign legacy or malformed manifests, and requires at least one `approved` reviewer. `generateProvenanceSigningKeyPair()` creates Ed25519 JWK key pairs for operator or CI use. Store signed envelopes as `provenance/runs/<run>.signed.json`.

`verifySignedPublicProvenance(envelope, { trustedPublicKeys, expectedSubject? })` fails closed in a fixed order: strict envelope parse (version-2 manifests only, so version-1 downgrades and unknown fields are rejected, and the approved-reviewer lineage policy is re-checked); the embedded public key must match its SHA-256 fingerprint; the fingerprint must appear in the caller-supplied trusted keyring; the Ed25519 signature must verify against the trusted key (never the embedded key) over the recomputed canonical payload; and an optional `expectedSubject` must exactly match the manifest repository and immutable commit SHA. Any failed check throws; there is no partial-trust path, and an empty keyring trusts nothing.

The pure signing library authenticates the signer's claimed lineage and subject; it does not fetch GitHub review state. The public CLI consumers below retrieve current native GitHub reviews. Keyring distribution and management still belong to the operator. Material merge-gate wiring and the encrypted private half of issue #61 — private bundles, remote sinks, OIDC identity, retention/Object Lock and audited reads — remain deferred behind ADR-0006's independent security review and explicit human approval gates.

This public contract deliberately does not include a private provenance sink, encryption material, bucket identity, or long-lived credentials. Those remain a separately reviewed issue #61 capability using short-lived runtime identity.

## Signed commands and current GitHub reviews

The existing unsigned `create` and `validate` commands retain their behavior. `sign` and `verify` consume the same public-v2 manifest and envelope-v1 codec with independently supplied public GitHub repository, current PR head SHA and PR number. They use the installed `gh` CLI and its normal authentication to issue a fixed read-only query against `github.com`; they do not create checks, change settings or decide whether a PR may merge.

```bash
bootstrap provenance sign --input manifest.json --output signed.json --private-key selected-ed25519.jwk.json --repository acme/widget --commit 0123456789012345678901234567890123456789 --pr 123
bootstrap provenance verify --input signed.json --keyring trusted-public-jwks.json --repository acme/widget --commit 0123456789012345678901234567890123456789 --pr 123
```

Replace the example repository, SHA and PR with independently verified context. The subject is the actual PR head, including a verified public fork head. A different squash merge SHA needs its own provenance and lineage contract; identical trees are not treated as identical subjects. Both commands require native `reviewDecision: APPROVED` and at least one independent approval submitted at the exact expected head. They collect the complete bounded `latestOpinionatedReviews` connection, check PR/base/head/author identity throughout pagination and repeat the collection. They do not infer the current opinion from review IDs or later comments. Current independent approved/commented/changes-requested opinions are recorded in lowercase-login order; old-head, pending, dismissed and author-comment rows cannot create approval. Missing identities, ambiguous rows, incomplete pagination and observed changes fail closed.

`sign` validates the existing public manifest and expected subject, replaces its claimed reviewers with the observed set, uses the selected local Ed25519 private JWK and checks the resulting signature. It rechecks reviewers before creating the output. The private file must have only `kty: OKP`, `crv: Ed25519`, and canonical 32-byte base64url `x` and `d` fields; mismatched public/private identity is rejected. Key bytes are never arguments to `gh`, public output or diagnostics. `verify` first checks strict schemas, separate trusted keys, signature and expected subject; invalid or untrusted envelopes make no GitHub request. It then retrieves current native lineage and requires the signed reviewer array to match exactly. The keyring is a nonempty JSON array of at most 64 unique strict public JWKs with only `kty`, `crv` and `x`; embedded keys never enroll themselves, and private or unknown fields are rejected.

Inputs are bounded regular JSON files opened without following symlinks. The signed commands require OS support for no-follow and nonblocking input opens and fail before input/network when those capabilities are unavailable; the unsigned commands retain their existing platform behavior. Manifest/envelope input and output are limited to 1 MiB, the private key to 4 KiB and the keyring to 64 KiB. The output directory must already exist. A private staging file is fully written and synced before an exclusive hard-link publication, so existing files or symlinks are preserved. Owned staging is cleaned on success/failure; a cleanup error is a failed operation even if the complete output was already linked. This is an atomic local visibility/collision guarantee, not a power-loss or hostile-same-user filesystem guarantee.

Each lookup is limited to 16 pages of 100 reviewers per complete collection, 1 MiB combined subprocess output per request, 30 seconds per request and 120 seconds overall. The subprocess has no shell or interactive prompts; failed/oversized/timed-out requests and remote errors produce sanitized diagnostics. A trusted installed `gh`, local OS/tooling and its configured GitHub authentication remain operator prerequisites. No remote service or live key enrollment is installed by this source change. The executable-fixture integration is qualified on Darwin; the corresponding POSIX fixture is intentionally skipped on Windows rather than treated as Windows execution evidence.

The result is a current observation, not an atomic GitHub snapshot: reviews can change after the final read. PR context is independently supplied to the consumer, not added to the signed wire format. Only the repository, immutable commit and reviewer set are checked against the independently expected PR context. The subject ref, workflow execution, provider, model, prompt and timestamp fields remain signer claims unless separately bound to authentic run evidence. The CLI does not unify the separate Cosign AI-attestation format, implement private capture or install a material required check. It therefore does not by itself establish all acceptance for #63 or #161.
