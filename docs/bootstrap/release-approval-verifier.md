# Release approval comparison prototype

These inactive source components compare a canonical approval manifest against facts independently collected by trusted adapters. The GitHub reader can retrieve PR and review facts using a caller-supplied token, but no release workflow invokes it. Tests use fabricated responses and a fabricated token; no real credential or release has been used.

The manifest binds the new-release publication action, repository identity, tag, version and channel, source commit and tree, workflow ID, path and revision, run and attempt, artifact and archive digest, original requester, attempt actor, and a sorted unique list of asset names, sizes and SHA-256 digests. The trusted adapter must derive the original actor and attempt actor separately for both preflight and publication from GitHub's run `actor` and `triggering_actor`; on a rerun those identities may differ. For Bootstrap's `v`-prefixed releases, the tag must equal the version; `rc` and `beta` channels require an rc/beta prerelease, and stable and maintenance require an unsuffixed release. Its canonical JSON encoding uses recursively sorted object keys, compact UTF-8 and one trailing newline. Comparison requires the actual facts to match exactly, including every asset. An authorized reviewer must submit an approval on the same current PR head with body `APPROVE-RELEASE-SHA256 <sha256-of-exact-manifest-bytes>`. The PR must contain only the selected approval manifest, and its author, requester, publisher and both attempt actors must differ from the authorized reviewer. Dismissals, later changes requested, ambiguous review ordering, expiration and changes to bound values fail closed. A later comment does not itself supersede an earlier review decision. The approval identifier alone does not prevent replay; the publication protocol must define and enforce reuse and retry rules.

The GitHub reader makes fixed-origin, read-only requests without following redirects, bounds response and pagination sizes, checks the manifest's Git blob hash, reads the review history twice, and verifies that the PR head and base stay stable. A separate metadata reader checks a caller-selected trusted workflow path and revision, the exact successful run and attempt, both preflight actors, the artifact's reported digest and the target commit tree through GitHub. It reads those facts twice. The artifact API identifies its run but does not by itself bind that artifact to a particular attempt: a partial rerun can retain outputs from an earlier attempt. The reader marks that binding, the reusable workflow identity, the archive bytes and target-source bytes as unverified. The readers rely on GitHub's authenticated API and on the caller supplying an appropriately scoped token and trusted repository and workflow identities. They do not download or hash the archive, establish that extracted asset bytes came from it, prove the target source archive, or identify publication actors. Other trusted code must establish those facts, and the caller must re-read approval and relevant immutable values at the publication boundary. These components cannot prevent a concurrent change after a check.

GitHub documents that a [rerun can have a different triggering actor while retaining the original actor's privileges](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs). The caller supplies a positive approval-validity limit, capped here at 24 hours; that cap is an implementation ceiling, not an adopted operating policy. Deployment still needs an accepted expiry and retry policy, a reviewed authenticated adapter, provider-bound race and immutability controls, independent review, and the owner's authorization for an actual release. No synthetic test is evidence of real human approval.
