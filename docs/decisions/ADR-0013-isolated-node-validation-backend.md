# ADR-0013: Isolate Node validation before fleet executor integration

Status: Accepted

Date: 2026-11-08

Decision owners: Bootstrap maintainers

Governing issue: [#62](https://github.com/OMT-Global/bootstrap/issues/62)

## Context

The prepared fleet executor ran repository-controlled checks and commit hooks in the authenticated operator context. Verified public origin, a clean checkout, and a current default-branch SHA do not grant target code access to cross-repository credentials, home files, agent sockets, or the network. The executor was extracted from the consolidation lane and preserved separately while this boundary is addressed.

A separate software-architect agent independently reviewed the [frozen isolation proposal](../security/fleet-isolation-design.md) at SHA-256 `b44c9b9b7f9e53a68b19430ae1607d1e39de94fbd1b4c76de5012088894ef6ca` and found no architecture blocker to this bounded backend stage. This records coordinator adoption of that architecture after an independent automated review. It does not replace exact-head GitHub approval or establish that the implementation confines code successfully.

## Decision

Implement one code-owned `node-npm-linux-v1` profile for Linux/amd64, pinned to the Microsoft Dev Containers Linux/amd64 image `mcr.microsoft.com/devcontainers/javascript-node@sha256:447fa75fbc7123952284b50229148e933ea756c40718601fa0ec46edd29fd0c6`. Probe Bash, Git, Python 3, Node 24, npm, and jq in that exact image, including a fixed jq JSON functional check, before any target-controlled phase. A missing/incompatible runtime or tool blocks; no host-shell, VM-start, or networked-validation fallback is permitted.

The coordinator adopted a material six-tool image amendment after independent architecture review. The [image provenance record](../security/node-npm-linux-v1-image.md) documents its OCI identities, root/development defaults, public environment, source-chain limitations, and Node 24.22.1 metadata versus the old image's actual 24.22.2. No security-parity or independently verified signature claim follows. Retain numeric non-root execution, fixed entrypoint/PATH/HOME/npm configuration, no-new-privileges, capability drop, and every existing filesystem/network/resource boundary. Public inherited image variables are trusted defaults rather than claimed absent. Actual tests must prove `sudo -n id -u` cannot obtain UID 0 under kernel `NoNewPrivs=1`. The new image remains runtime-unproven until the complete hosted gate passes.

The backend accepts only explicitly frozen public source and sanitized Git data from a future trusted supervisor. It must not import the original checkout's Git/configuration, ignored files, credentials, home, caches, or sockets. Dependency preparation accepts only bounded public npm-registry archives with verified SHA-512 integrity; download them as inert data without authentication or redirects. Cache preparation and installation run offline with lifecycle scripts disabled. No target code executes online.

Run validation and required-hook replay in independent fresh containers with networking disabled, a read-only root and prepared source/index, non-root target execution, no Linux capabilities, no-new-privileges, explicit resource/tmpfs/source/download/output bounds (including 10,000 total source file/directory entries and depth 32), and cleanup on every exit path. Permit only profile-owned writable temporary/dependency/build locations. Do not bind-mount host paths or accept target-provided Docker arguments. Killing a client process alone is insufficient cleanup.

A trusted inert non-root container must hold the three bounded Docker local-driver tmpfs volumes continuously, starting before data copy. Check its live state before preparation, each target phase, and successful evidence; its loss blocks. A shared absolute 60-minute deadline bounds each backend call through both a host watchdog and keeper timer. The keeper has 0.1 CPU, 64 MiB memory/swap, 16 PIDs, and 1 MiB temporary storage. Create reserved dependency/build mount directories during writable preparation. Each fresh hook/check container must independently copy the pristine cache and run the locked offline install with lifecycle scripts disabled before target entry. Explicitly disable daemon logging with `--log-driver none` for every container, retain only bounded attached output, and remove workers before the keeper and volumes. These storage, dependency, and output refinements require the new runtime delta review and actual hosted proof recorded separately.

Permit execution on actual hook/check `node_modules` tmpfs for installed `.bin` and native tools, and on their existing 256 MiB `/tmp` for temporary native/script helpers used by repository checks. Preparation `/tmp` remains 256 MiB and non-executable; keeper `/tmp` remains 1 MiB and non-executable. Installer, cache, and build tmpfs also remain explicitly `noexec`. Keep existing sizes, ownership, `nosuid`/`nodev`, read-only source/index, offline execution, credentials, privileges, resource bounds, and timeouts. The trusted helper uses an internal boolean defaulting to non-executable and enables it only at these fixed target-phase call sites; no public option or target path selects this capability. Required runtime proof directly executes the already locked TypeScript compiler and a fresh temporary shebang helper in both phases, with configured and kernel mount-flag assertions. The [review record](../security/fleet-isolation-implementation-review-2026-11-08.md#bounded-executable-temporary-helper-amendment) records the earlier dependency-only scope, the independently clean implemented amendment, and pending runtime acceptance.

The initial hook contract supports no executable hook or a regular in-repository `.githooks/pre-commit`, bound to the prepared source/index/base. Other effective executable hooks, external hook paths, unsupported toolchains, workspaces, private dependencies, and authentication-bearing npm configuration fail closed. The supported hook context is a normal root-directory, no-editor, all-staged, single-parent commit. The trusted supervisor supplies planned public author/committer name, email, and raw Git date; the backend provides no defaults or identity inference. Hook replay exports the prepared `.git/index`, empty `GIT_PREFIX`, `GIT_EDITOR=:`, and both planned identities/dates, while local Git user identity matches the planned committer. Partial commits, merges, amendments, subdirectory-prefix and editor contexts are unsupported. The backend exposes distinct `prepared-hook` and `final-check` phases. The first binds the hook to base HEAD and the prepared index; the second verifies the supplied final candidate has exactly the expected parent, raw author and committer identities/dates, message, and raw prepared tree before running checks with that candidate as clean HEAD. The backend never treats a sandbox-produced tree or claimed digest as authority to sign or publish.

The declared native baseline is `git --git-dir=.git -c core.hooksPath=.githooks commit --file=<public-message>` at the repository root, with the frozen message already present in `.git/COMMIT_EDITMSG`. Replay uses `git --git-dir=.git -c core.hooksPath=.githooks hook run pre-commit` with the planned environment above. Git supplies `GIT_DIR=.git` and the effective hook configuration; preparation keeps `core.hooksPath=/disabled-hooks`, and only this authorized phase receives the command-scoped override. This supports the declared Git context, not arbitrary ambient message timing or OS/process introspection equivalence.

This stage supplies the backend and tests only. The separate supervisor integration must construct a disposable publication repository, independently verify the frozen raw tree, replay required hooks in isolation, create/sign the exact commit through trusted Git plumbing, validate that exact final commit, and perform create-only publication after review. Repository hooks/filters/fsmonitor/remote helpers must never execute in the credentialed host context. The original checkout remains unchanged.

## Validation and activation boundary

The separate [implementation review](../security/fleet-isolation-implementation-review-2026-11-08.md) records exact source hashes and its remaining runtime-evidence boundary. Run meaningful local regression tests and independent source-delta review, then actual hosted Docker tests at an exact committed revision. Complete the required final branch autoreview after that runtime evidence and any resulting fixes, before opening a PR or claiming readiness. Before the new standalone workflow is registered on the default branch, dispatch the existing [Full Release Validation](../../.github/workflows/full-release-validation.yml) caller from the backend branch with `release_profile=full`; its reviewed extended script requires the Docker suite. The new [manual hosted workflow](../../.github/workflows/fleet-isolation-validation.yml) is a post-merge convenience route, not an assumed pre-merge dispatch capability. Actual image/tool probes, locked offline installation, validation, hook behavior, hostile environment/file/socket/network canaries, immutable prepared source, imports from the locked dependency in both fresh phases, storage-keeper death in both phases, actual storage/log-driver inspection, cancellation cleanup, and unsupported-input guards are required evidence. Argument spies and a passing unit suite do not establish confinement.

Local Docker was unavailable while the design was prepared. Runtime readiness remains pending until the real hosted suite passes. Acceptance of this architecture neither enables a fleet apply command nor authorizes live target mutation, remote settings, signing/publishing operations, merge automation, or a production rollout. Keep #62 open through supervisor integration and its acceptance evidence.

## Consequences

- The first profile deliberately supports a smaller runtime surface than the eventual polyglot fleet inventory.
- Docker/kernel, selected image, and trusted supervisor/tooling remain trust boundaries; this does not claim resistance to their compromise.
- Other toolchains, private registries, broader hook lifecycles, macOS sandboxing, and runtime provisioning need separate reviewed profiles.
- Missing evidence, unsupported behavior, and incomplete cleanup remain explicit failures rather than implicit permission to run on the host.
