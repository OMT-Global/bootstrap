# Proposed isolated fleet execution contract

Status: Proposed for independent design review; not implementation approval or a record of isolation evidence.

Governing issue: OMT-Global/bootstrap#62. Prepared 2026-11-08 from saved executor commit `0e7a1d2953c4546f45db7e671e2dcac795ec4bee`. The unsafe executor is being removed from the consolidation lane and preserved separately. No runtime was installed or started for this design.

## Assumptions, constraints, and risks

- The supervisor, reviewed Bootstrap generator, Git/Docker/Node tooling, selected toolchain image, signing program, and fleet credential broker are trusted. Target repository code, tests, dependency contents, attributes, and hooks are not trusted with that authority, even when their public identity/default-branch SHA is verified.
- Preserve explicit allowlists, immutable policy/generator inputs, pilot gates, literal scoped changes, independent review, configured signing, DCO, and recovery evidence. No target-controlled command receives operator credentials or host home/config/agent/socket access.
- The first implementation is Linux/amd64 Node/npm only. It is sufficient to exercise Bootstrap's CLI-class path; it does not claim Python, Swift, native, arbitrary polyglot, private-registry, or workspace support. Unsupported targets block before mutation. A later profile requires its own reviewed implementation and tests.
- Containers share the host kernel. This boundary does not claim protection against a Docker/kernel vulnerability or a malicious trusted supervisor/image. Host administrators remain trusted. Resource exhaustion, incomplete cleanup, wrong snapshots, hook omission, and online dependency execution are explicit failure modes to test.

## Decision 1: use a disposable publication repository

Do not bolt a sandbox around just the existing `bash` call. Operate the proposed upgrade in a fresh disposable repository controlled by the supervisor. Leave the user's source checkout unchanged throughout preparation, validation, signing, and publication.

1. Verify the allowlisted public identity, live default ref/SHA, policy source, input evidence, and local identity as before. Resolve trusted absolute tool paths before entering any target directory. The only original-checkout Git operations are audited metadata reads such as `rev-parse`, `symbolic-ref`, `config --no-includes --local --get`, and byte-safe tracked/untracked inventories; do not run its `status`, checkout, add, commit, or push under operator authority. Read regular tracked files/modes without invoking filters, and fail if the required clean/raw-byte comparison cannot be established. Local Git configuration is metadata, not executable policy authorization. Initial implementation review must verify each chosen read command cannot invoke target filters/hooks; remove a command if that property cannot be established.
2. Fetch the already-verified public base into a new supervisor-created bare repository using the literal approved HTTPS URL and SHA. Do not copy the target's `.git`, config, templates, hooks, alternates, credential helpers, or worktree metadata. Its original local source may be used only after byte/mode comparison with that base; a Git object export is data, not a configuration export.
3. Materialize public tree blobs as ordinary files without `git checkout` or smudge filters, then apply the trusted renderer to that isolated staging tree. Reject submodules, symlinks, hardlinks, special files, unsafe paths, required external filters/encodings, and unsupported hook/configuration cases in this first profile. Do not copy untracked checkout contents, installed dependencies, home assets, or Git-local state.
4. Freeze a prepared-tree manifest: byte-safe paths, raw blob hashes, executable modes, base SHA, generator/policy identities, profile/image identity, lockfile hash, intended commit message/DCO, and changed-path inventory. Confirm unchanged paths equal the public base and changed paths equal the reviewed allowlist. The supervisor's expected tree is authoritative; no sandbox-produced tree or claimed hash can replace it.

The fresh repository is also the recovery location. On failure, report a bounded recovery directory plus phase/reason and keep public prepared source/objects only when useful. It must contain no persisted credentials. Never reset or clean the user's checkout. This intentionally replaces original-worktree branch mutation/restoration with safer disposable preparation; document that operator-facing change in the new ADR/runbook.

## Decision 2: one concrete supported profile

Define a trusted code-owned profile `node-npm-linux-v1`, not an arbitrary shell callback or target-supplied Docker argument list. Its reviewed record contains:

- one official Node 24 Debian bookworm OCI image resolved to a real immutable digest during implementation, with explicit `linux/amd64` platform; verify Bash, Git, Python 3, Node, and npm versions needed by Bootstrap before selecting the digest;
- a fixed validation entry point, `bash scripts/ci/run-fast-checks.sh`, and fixed internal Git/hook orchestration;
- npm lockfile v2/v3 at the repository root, no workspaces, no alternate package managers, no Git/file/link/private dependencies, and no authentication-bearing npm configuration;
- an exact supported hook policy: either no executable hooks or the regular in-repository `.githooks/pre-commit`. Block any other executable effective hook, an external/global hook directory, or unsupported hook configuration. Do not silently omit it;
- explicit limits: 15-minute phase timeout, 2 CPUs, 4 GiB memory, 256 PIDs, bounded tmpfs workspace/cache, at most 10,000 copied entries/512 MiB source data, bounded dependency archives and aggregate download size, and 8 MiB combined retained output. Exceeding any bound fails with a sanitized reason.

These are proposed operational limits, not existing guarantees. Their values and image digest must be reviewed and exercised before acceptance. A missing Docker CLI/daemon, incompatible engine/platform, unavailable image, invalid lockfile, missing cache entry, unsupported engine/tool requirement, or unsupported hook produces a preflight block. There is no automatic VM startup, install, privileged mode, host-network mode, or host-shell fallback.

## Decision 3: dependency data preparation without running repository code online

The validation container never has external networking. Prefer an entirely offline container pipeline rather than trying to implement a registry firewall inside Docker.

1. A trusted supervisor downloader reads the frozen npm lockfile as data. Require public `https://registry.npmjs.org/` tarball URLs, no credentials/query/fragment, supported SHA-512 integrity, no redirects, bounded response size/count, and exact integrity before accepting bytes. It sends no operator authentication or arbitrary repository headers. Downloading inert public archives is separate from executing dependency code.
2. Pass only those verified archives and the two regular package manifests into a fresh credential-free installer area. Use the pinned image's trusted npm commands to populate an ephemeral cache and run `npm ci --offline --ignore-scripts --no-audit --no-fund --engine-strict` with empty user/global npm configuration. No target `.npmrc`, source scripts, lifecycle hooks, SSH agent, home cache, or credentials participate.
3. Prove in the integration test that npm's cache populated from those exact tarballs satisfies the locked offline install; do not assume cache-key behavior. If complete offline installation cannot be demonstrated, block rather than enable network for validation. Package extraction is still performed by trusted, pinned npm and is part of its parser trust boundary.
4. Run the actual repository check entry point offline with the prepared source and that cache. Its own `npm ci` is constrained by `NPM_CONFIG_OFFLINE=true` and empty credential configuration. Repository tests and lifecycle code may execute here, within the isolation boundary. No cache is imported from or exported into the operator's home.

If this stricter cache approach proves incompatible, the alternative is a separately reviewed credential-free installer with registry-only egress and lifecycle execution disabled. A broad networked install is not an undocumented fallback for this design.

## Decision 4: container confinement and data transfer

Create named disposable containers using only trusted, fixed arguments. Override the image entry point/healthcheck. Use network `none`, read-only root filesystem, no Linux capabilities, no-new-privileges, private namespaces, non-root execution for target-controlled code, resource limits, and bounded temporary storage. The image must supply the named non-root user.

Never bind-mount the source checkout, publication repository, home, Docker socket, SSH/GPG agent, runtime configuration, host caches, or arbitrary host paths. Transfer bounded data into the disposable container using a reviewed supervisor protocol; Docker-managed filesystem/tmpfs is not authority to access other host paths. Any trusted root-only setup must finish before target-controlled execution and must not receive credentials. Preserve the original executable-bit manifest separately when permissions are adjusted for the non-root sandbox.

Use an explicit minimal environment (fixed PATH, isolated HOME, CI flag, offline npm/cache locations). Do not forward arbitrary parent variables, `GH_TOKEN`, Git credential settings, proxy credentials, SSH/GPG sockets, Docker configuration, or process-injection variables. Capture bounded output as untrusted text and redact before report publication.

Use fresh execution containers for required-hook replay and validation, populated independently from the same supervisor-frozen source and pristine dependency cache. Do not reuse filesystem state changed by repository tests as the input to the hook phase. For the initial Node profile, mount prepared source and its sanitized Git metadata read-only from Docker-managed storage; permit bounded writable mounts only for `/tmp`, npm cache, `node_modules`, and `dist`. Reject tracked content at reserved writable mount paths rather than hiding reviewed files beneath a mount. No host path is mounted. Set Git optional locking off for read-only inspection. The actual npm/Vitest/TypeScript entry point must prove it works with those writable locations; a target needing other writes is unsupported until its profile is reviewed. This enforces prepared-source immutability instead of trusting a repository process's post-run hash report. Ensure a target cannot keep a background process alive into another phase; remove each phase container before progressing.

The supervisor records container identity before starting work and removes/kills the container and ephemeral storage in a `finally` path after success, failure, timeout, cancellation, or partial startup. Killing the Docker CLI alone is insufficient. Cleanup failure must preserve the primary failure and be reported; it must not turn missing validation into success.

Docker's documented network-none and runtime controls support this proposal, but availability of those flags is not evidence that this implementation enforces them: [network isolation](https://docs.docker.com/engine/network/drivers/none/), [runtime options](https://docs.docker.com/reference/cli/docker/container/run/).

## Decision 5: required hooks and credentialed Git operations

For the first supported profile, only an in-repository pre-commit hook is supported. This covers Bootstrap's current generated hook. Other hook lifecycles are deliberately unsupported until their exact arguments/timing/effects are implemented and reviewed. Explicitly inventory effective hooks including `post-checkout`, `prepare-commit-msg`, `commit-msg`, `post-commit`, and `pre-push`; block their executable presence rather than assuming they cannot matter.

In the fresh hook container, construct a sanitized Git context from the public base object bundle and the exact prepared files. Do not import original `.git/config`, credential helpers, include paths, external filter commands, hooks, signing settings, or host config. Create the proposed index from the expected raw bytes/modes without filters. Set the proposed branch/base/index context needed by the supported pre-commit hook, replay that exact hook with Git's documented pre-commit invocation semantics, and require success. Bind its regular path and content hash to the prepared manifest. Required scanners/scripts it invokes run within the same sandbox. Keep prepared source/index read-only; any hook attempting mutation fails. Do not copy sandbox-generated objects, source, or configuration back to the host.

After the supported pre-commit hook passes, the supervisor independently reconstructs/verifies the publication tree from its own frozen bytes, never accepting a hook-produced object/tree claim. It creates the final DCO-bearing commit through trusted Git plumbing (`hash-object --stdin --no-filters`, an explicit index/tree, and `commit-tree` with the verified base parent/message), using the operator's configured signing identity/program only in the trusted host process. Read the resulting commit back and verify tree, parent, full message, author/committer metadata, and configured signature requirements. Unsupported signing configuration fails closed; no global signing setting changes. The object may exist locally before validation succeeds, but no remote ref or source checkout is changed.

Next, populate the independent validation container with that exact final public commit as its clean HEAD and the same frozen source. This gives repository checks meaningful Git identity without host Git configuration or keys. Run the check entry point, then discard the container. This ordering avoids claiming validation of a different unsigned/staged tree or inheriting side effects from a prior untrusted phase. A later signing/commit amendment invalidates the exact-commit evidence and requires revalidation/review.

Use only the supervisor-created repository/config for publication. Repository-owned hooks/filters must not execute in credentialed host operations. The fixed trusted empty host hooks directory is explicit and recorded because the supported required pre-commit policy has already been replayed on the exact tree; it is not a silent `--no-verify` bypass. The profile preflight blocks any effective pre-push/post-commit/other executable hook rather than omitting its required behavior. More hook support needs a later contract, including exact final commit/ref inputs and replay evidence.

Run autoreview on this final prepared commit/diff through the existing reviewed helper. Recheck that its exact commit and prepared files are unchanged. Only the supervisor then receives/uses fleet credentials for literal allowlisted remote operations. Create a fresh branch with an atomic nonexistence expectation; never overwrite an existing recovery branch. Use a reviewed Git create-only lease or equivalent provider primitive, and test its race behavior. Create only the draft PR; no settings, approval, auto-merge, or merge action.

Git documents bundle-based object transfer and low-level commit construction independently of worktree checkout: [git bundle](https://git-scm.com/docs/git-bundle), [git commit-tree](https://git-scm.com/docs/git-commit-tree). Attribute conversion must not be accidentally invoked by the supervisor: [gitattributes](https://git-scm.com/docs/gitattributes). Hook replay must follow the supported lifecycle exactly: [Git hooks](https://git-scm.com/docs/githooks).

## Exact acceptance plan

Unit tests are necessary but cannot establish confinement. Required hosted Linux/Docker integration tests must exercise the actual backend before it is described as usable:

1. Run an actual minimal locked Node repository and Bootstrap's real fast checks from a prepared tree; prove offline dependency cache completeness and meaningful test execution.
2. Set fake operator environment/file/socket canaries and a harmless outside-workspace file. A target script and supported hook must fail to read/use them or change the host file. Never use actual credentials for this test.
3. Attempt external DNS/IP/host/metadata-server connections from repository code and hook code; verify no external route. Test loopback-local unit servers independently so legitimate local tests remain possible.
4. Place malicious repo `.npmrc`, lifecycle scripts, attributes/filter declarations, unsupported hooks, symlinks/submodules, oversized files, forged cache archives, mutable image input, unsupported platform/runtime, and missing offline packages. Assert the documented early block or contained failure, never a host fallback.
5. Prove the hook ran against the expected staged diff/base and that failing or mutating hooks prevent signing/push. Assert no repository-owned host hook/filter executes during final commit construction or push. Preserve signing requirements with synthetic test keys only.
6. Fail validation, hook, timeout, cancellation, container startup, cache preparation, cleanup, signing, review, push, and PR creation separately. Verify original checkout unchanged, no container/volume left on normal cleanup, recovery metadata truthful, no push before all gates, and primary errors preserved.
7. Verify final commit parent/tree/message/raw bytes/modes and report identity against the frozen supervisor manifest; reject sandbox-supplied alternate trees/objects and post-validation changes. Exercise odd filenames and deletions.
8. Test fresh-branch creation races and unchanged class/pilot/batch behavior using the actual new supervisor path. A failed isolated validation stops its class; unrelated supported classes retain documented behavior. Unsupported profiles never consume a mutation attempt or create a remote branch.

The integration workflow must run on GitHub-hosted isolation, use no production fleet credentials, and exercise disposable local repositories plus fake remote endpoints or a separately authorized scratch target. Unit-spy assertions about Docker arguments are not a substitute. Local Docker was unavailable during design, so local confinement/e2e proof is explicitly absent.

## Implementation boundary and estimate

Separate the work into an isolation backend/profile with actual e2e tests, then executor integration using disposable publication repositories. Do not expand PR203's nearly full 800-line budget or reintroduce the unsafe executor before both are reviewed. Expect roughly 350–550 non-test lines for the backend/cache/snapshot lifecycle and 150–250 changed lines for supervisor integration, plus tests/docs; measure actual diffs and split coherent PRs if required. These are estimates, not permission to compress safety logic or exclude semantic files from review.

Before implementation, independent design review must decide the following concrete proposed choices: Node-only Linux/amd64 initial support; code-owned immutable image and limits; registry-tarball/cache strategy; only no-hook/pre-commit hook support; raw-tree/no-filter publication semantics; configured signing through trusted plumbing; original checkout unchanged with disposable recovery; and create-only remote branch publication. Resolve those in an Accepted ADR with exact compatibility/non-goals. No new storage service or paid provider choice is required. Other profiles, external/private dependencies, broader hook behavior, macOS sandboxing, and remote runtime provisioning remain outside this first stage.

## Why not a quick macOS sandbox-exec patch

`sandbox-exec` exists on this host, while Docker/Podman/bwrap were unavailable; Colima was installed but stopped and Lima reported no instances. Binary reachability alone does not establish a complete filesystem/network/process policy. A macOS-only profile would still need dependency/toolchain access rules, hook handling, signing separation, adversarial tests, and a Linux alternative. It is not simpler for this repository's cross-platform fleet contract and should not become an implicit fallback. No local runtime or VM should be started merely to hide that current e2e proof is unavailable.

## Independent review and backend-stage disposition

The proposal above is preserved byte-for-byte from the original design package, SHA-256 `b44c9b9b7f9e53a68b19430ae1607d1e39de94fbd1b4c76de5012088894ef6ca`. Its Proposed status, source commit, implementation estimate, and consolidation-budget statements describe that historical review target. The unsafe executor was subsequently extracted from PR #203; this document does not report the old executor as available or the current consolidation as nearly at its limit.

On 2026-11-08, a separate Codex software-architect reviewer who did not author the proposal reviewed those exact bytes, the saved executor paths, and the cited Docker/Git contracts. No concrete architecture blocker remained for the bounded `node-npm-linux-v1` design. The reviewer specifically required implementation proof for host Git configuration paths, including fsmonitor, filters, textconv, hooks, remote helpers, and rewrite settings. This is an independent automated design review, not a GitHub approval, human production authorization, or confinement test.

[ADR-0013](../decisions/ADR-0013-isolated-node-validation-backend.md) accepts only the backend-stage architecture. This stage introduces neither a fleet CLI apply command nor signing, push, PR creation, or live-repository mutation. Disposable publication-repository construction and trusted signing/publication remain a separate supervisor integration stage. Both stages and the exact runtime evidence must be reviewed before #62 can close.

The selected profile candidate is `docker.io/library/node@sha256:6b9d4ea31e614e29f364bf75758458731eb1e105b80c99667438dd6b3fe262e0`, Linux/amd64. Registry index/manifest/config digests were checked against the publisher's bytes and [official-images source](https://github.com/docker-library/official-images/blob/f46f6995a0b94aef7d593071fca3b4af924ffe12/library/node), which selects [Node's immutable Dockerfile](https://github.com/nodejs/docker-node/blob/e994dfe115899a82684caa7533380aa7d439aae1/24/bookworm/Dockerfile). Metadata declares Node 24.22.2; source/package evidence supports Bash, Git, Python 3, Node, and npm. That is not executed tool-version proof or independent image-signature attestation.

Actual isolated probes for all five tools, offline-cache completeness, and hostile Docker integration tests remain mandatory. Local Docker/Podman was unavailable during design; no runtime or VM was installed or started. Actual hosted validation must run at the exact reviewed source revision and fail when the Docker suite cannot execute. Before the new workflow is registered on the default branch, use the existing [Full Release Validation](../../.github/workflows/full-release-validation.yml) caller on the reviewed backend branch with `release_profile=full`; the reviewed extended-script projection requires integration tests for that route. The new [standalone manual workflow](../../.github/workflows/fleet-isolation-validation.yml) remains a post-merge convenience. The backend keeps `prepared-hook` and `final-check` phases distinct; the latter verifies the supplied candidate parent/message/tree and uses that exact candidate as clean HEAD. Until that evidence exists, treat the profile as unproven and unavailable for live fleet execution.
