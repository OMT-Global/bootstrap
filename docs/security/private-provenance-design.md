Compliance mode would remove the ordinary ability to shorten retention and needs separate explicit approval before use.

## Proposed flow and trust boundaries

1. Trusted capture receives the expected repository, immutable commit SHA, run identifier, signed public envelope, and permitted private evidence. Verify public signer trust, exact subject, and equality of the expected run identifier with the public manifest run identifier, then reject unknown fields, oversized inputs, prohibited categories, and recognized credential literals before encryption.
2. Canonicalize a base binding of private-format version, algorithm identifier, repository, commit SHA, run identifier, and signed-public-envelope digest. Call AWS KMS `GenerateDataKey` with `KeySpec: AES_256`, an allowlisted symmetric key ARN from trusted runtime configuration, and encryption context containing only a protocol domain/version and the base-binding digest. KMS context is logged and must contain no private payload or secrets. Validate the returned key identity and length. Add the trusted key ARN and ciphertext-key digest to the authenticated header, then use its canonical bytes as AES-256-GCM additional authenticated data with the new data key and a fresh 96-bit nonce.
3. Build a strict ciphertext envelope containing the authenticated header, nonce, ciphertext, authentication tag, and KMS ciphertext data key. Clear mutable plaintext key buffers after use and do not write plaintext temporary files. Put the envelope under an opaque capture identifier with `If-None-Match: *`, a SHA-256 checksum, the approved Governance retain-until date, and SSE-KMS using the separate S3 service-encryption key. Bucket policy enforces these requirements; writer IAM has no stored-object read or client-key decrypt permission. Object Lock alone cannot enforce create-only keys.
4. Through a separate ciphertext-verification role, confirm the exact stored version, SHA-256 digest (not an ETag assumption), and Governance retention state against the approved 90-day policy. This role can inspect ciphertext and use the S3 service-encryption key as needed, but cannot unwrap the client-envelope data key. Only then issue a signed capture receipt for the private evidence channel. A required check verifies receipt signer trust, expected subject/run/public digest, stored ciphertext digest, retention, and the approved material-review policy for the current PR head.
5. The requester authenticates to a trusted read broker and presents a specific, authenticated approval from the approved read authority bound to purpose, exact object version/subject, requester, and bounded access period; PR-body text or a caller-supplied approval flag is insufficient. The broker alone holds combined S3 read, S3 service-key decrypt, and client-envelope-key decrypt access. It verifies the receipt and approved scope, durably records the attempt, and obtains a positive audit acknowledgment before it may release plaintext. It reconstructs the exact KMS context, verifies the trusted key ARN, authenticates/decrypts and revalidates in memory, and emits a completion/failure event. No requester receives S3/KMS STS credentials, an assumable decrypt role, or an alternate direct access path. Never return unauthenticated partial plaintext or release plaintext on missing audit acknowledgment.

The private sink and key service are separate trust boundaries. Public output remains the strict public envelope and sanitized check status. Possession of a ciphertext envelope is neither read authorization nor proof of successful material capture.

## Frozen candidate protocol framing

These are proposed version-1 constants for independent review, not an implemented format. Use the existing `sorted-json-v1` canonicalizer for every hashed/signed JSON object: recursively sorted keys, UTF-8, and no insignificant whitespace. Reject duplicate keys, invalid UTF-8, unknown fields, noncanonical encodings, and out-of-bounds values before cryptography. SHA-256 values are exactly 64 lowercase hexadecimal characters. Timestamps use UTC `YYYY-MM-DDTHH:mm:ss.sssZ`.

- Private input is `{ schemaVersion: 1, evidence: [{ category, text }] }`; `category` must belong to the separately approved category enum (still pending), be 1–40 ASCII letters/digits/hyphens, and `text` is 1–16,384 UTF-8 bytes. Limit evidence to 64 entries, nesting to four containers including the root, and both original input and canonical decrypted payload to 1,048,576 bytes. Enforce credential rejection across all fields and approved evidence categories before capture. The expected public envelope's canonical bytes are limited to 65,536 bytes for this private protocol.
- The base header fields are exactly `domain: "bootstrap-private-bundle"`, `envelopeVersion: 1`, `canonicalization: "sorted-json-v1"`, `algorithm: "aes-256-gcm"`, `subject: { repository, commitSha }`, `runId`, and `publicEnvelopeSha256`. Subject/run formats inherit the public schema, and all three must equal the verified expected public manifest. KMS context is exactly `{ domain: "bootstrap-private-bundle", version: "1", bindingSha256 }`, where the digest covers canonical base-header bytes. The final authenticated header adds only `kmsKeyArn` (trusted allowlist, at most 2,048 UTF-8 bytes) and `wrappedKeySha256`.
- Require a 32-byte plaintext data key, 12-byte nonce, and 16-byte GCM tag. The ciphertext envelope fields are exactly `header`, `nonce`, `ciphertext`, `tag`, and `wrappedKey`. Binary fields use canonical padded standard Base64 with no whitespace or URL alphabet; decoding and re-encoding must match exactly. Decoded ciphertext is 1–1,048,576 bytes, the KMS ciphertext key is 1–6,144 bytes, and decoded nonce/tag lengths are exact. Canonical envelope bytes are at most 2,097,152 bytes. Upload in one `PutObject` with a full-object SHA-256 checksum; no multipart/composite checksum is accepted in version 1.
- Receipt signing covers canonical payload fields exactly: `domain: "bootstrap-private-capture-receipt"`, `receiptVersion: 1`, `canonicalization: "sorted-json-v1"`, `algorithm: "ed25519"`, `subject`, `runId`, `publicEnvelopeSha256`, `ciphertextEnvelopeSha256`, `storage: { region, bucket, key, versionId }`, `capturedAt`, `retention: { policyId, mode, retainUntil }`, and `signedAt`. `storage.region` equals the approved region, bucket is at most 63 ASCII characters, key at most 1,024 UTF-8 bytes, nonempty version identifier at most 1,024 UTF-8 bytes, and policy identifier 1–128 ASCII letters/digits/dots/hyphens. Mode is `GOVERNANCE`; `retainUntil` is at least `capturedAt + 90 * 86400 seconds` under the approved capture clock policy. Storage fields are private and exact-version metadata must match them. The receipt envelope has only `payload` and `signature: { keyFingerprint, value }`; fingerprint is SHA-256 and signature is canonical Base64 decoding to 64 bytes. Bound the complete canonical receipt to 16,384 bytes and verify with an explicitly trusted receipt-signing key. The existing public Ed25519 envelope/domain is not repurposed or modified.

The implementation must express these constants as strict schemas and test byte-level vectors before remote use. A field or framing change requires an explicit version/design review; it cannot silently alter public version 2.

## Proposed adapter responsibilities

| Boundary | Required behavior | Prohibited shortcut |
|---|---|---|
| Client-envelope KMS key | `GenerateDataKey` for capture; `Decrypt` only inside the trusted broker for approved reads; exact encryption context and trusted ARN; reviewed rotation/recovery | Committed keys, writer decrypt grants, implicit trust in an envelope-supplied ARN, private data in logged encryption context |
| AWS S3 logical sink | Conditional create-only put, separate SSE-KMS key, exact-version SHA-256/retention verification, 90-day Governance lock, broker-only approved exact-version read | Object Lock as a replacement for conditional writes, ETag as SHA-256 proof, capture/read bypass or deletion grants |
| Audit channel | Durable create-only application attempt/outcome events; explicit CloudTrail S3 data events and KMS/STS/admin coverage; protected logs and validated digest chain | Payload logging, unaudited read, asynchronous CloudTrail delivery as synchronous read authorization |
| Capture receipt verifier | Strict versioned schema, independent signing trust, exact subject/run/digest binding, evidence freshness policy | Trusting caller-provided success booleans, unsigned receipts, stale evidence for a different PR head |
| Material gate | Trusted classification and exact-head GitHub review evidence, approved required-check configuration, failure on missing required capture | PR-author assertions as approval, private capture in a fork job, treating a local-only receipt as verified remote evidence |

## Identity, permissions, and audit review

Use GitHub OIDC to assume separate AWS roles with short sessions. IAM trust must constrain issuer, `aud=sts.amazonaws.com`, and an exact approved repository/environment `sub`; no organization-wide or repository-wildcard grants. An environment subject does not independently constrain workflow/ref/commit, so protected environments, controlled trusted workflow sources, verified execution metadata, and negative tests must close that boundary. Only the trusted broker workload may assume the private-read role, after verifying the requester and the approved read authority’s scoped approval. Broker sessions are narrowed to the approved object/version, KMS keys, and binding-context digest for the approved access period. Requesters cannot assume that role and receive no AWS credentials or direct S3/KMS access; a short-lived credential issued to the requester would still bypass the application audit gate and is prohibited. Do not run private capture or reads in fork jobs or execute untrusted PR code in the privileged capture process.

Keep client-envelope KMS authorization separate from S3 SSE-KMS authorization. The capture role may generate a current bundle's data key and put ciphertext, but cannot retrieve prior objects, unwrap keys, delete, alter retention, or assume administration roles. The ciphertext verifier can inspect stored ciphertext with only the S3 service-key permissions it needs. The broker-only private-read role can retrieve approved versions and unwrap permitted keys; it cannot write payload objects, change retention, or bypass it. The broker runs controlled code with no requester-supplied executable hooks; it gates all plaintext release on approval and synchronous durable audit acknowledgment. Key-policy, retention/break-glass, and audit administration are separately controlled; IAM configuration must not let ordinary roles grant themselves these capabilities.

The broker/runtime and cloud/key/audit administrators are explicit trusted operators. A compromised broker or administrator who changes policies can bypass ordinary-user controls; review and audit those privileged exceptions separately rather than claiming all human bypass is prevented. Released plaintext can be copied by its authorized recipient; subsequent copies are outside this storage-read gate.

Keep client-envelope keys decryptable for every retained bundle; rotation must preserve historic reads. Key disablement, scheduled deletion, grants, policy edits, and loss of unwrap permission affect availability even while S3 versions remain locked. Require a reviewed recovery/deletion policy and alerts for those operations; Governance lock does not protect KMS keys.

Configure CloudTrail S3 data-event selectors explicitly for capture, read, and audit evidence locations; data events are not enabled by default. Include KMS cryptographic operations and STS/IAM/S3 retention or policy administration in reviewed trail coverage. Protect delivered logs and digest files from capture/read modification, enable integrity digests and scheduled validation, monitor delivery/selector changes, and alert on bypass, destructive key changes, or reads without matching approval/application audit. CloudTrail is corroborating asynchronous evidence; required application audit acknowledgments gate plaintext release. Proposed audit retention is at least 90 days, with exact target/admin and cost approval pending. A separate audit account is preferred if available, not assumed to exist.

OIDC tokens, provider credentials, plaintext keys, physical object locations, and private payloads must not appear in generated manifests, receipts exposed publicly, logs, errors, or review output. Error messages identify a failed stage using bounded identifiers without echoing untrusted values.
